# Android verified-session retry

Android website verification runs in the app's WebView, whose CookieManager provides exact-URL cookies and its user agent to the regular catalog transport. A successful browser page does not establish that OkHttp or the ECH client can reach the same host: those clients use different network and TLS stacks. Returning from verification already triggers a new Explore search; it does not reuse the failed search result.

For a user-opened in-app verification origin, a connection failure on the public Danbooru `/posts.json` or numeric `/posts/{id}.json` endpoint can retry through Chromium's WebView network stack. A prior failed search causes the first post-verification request to try the browser route immediately. After a successful JSON-shaped response, only the exact origin is saved in app-private preferences so later eligible requests can use the route after process restart; cookies and tokens are never stored there, and the preferences are excluded from system backup and device transfer. An app-owned blank HTML document uses the exact HTTPS origin as its base URL; same-origin `fetch` supplies WebView's own cookies and user agent. The site homepage is not downloaded or executed by this retry. No API-key or authorization headers are passed into the document, and list query parameters are limited to tags, page, and limit. Both Dart and Android enforce origin and endpoint restrictions. Requests disallow redirects, file and content access, and mixed content; certificate failures are not bypassed. Two concurrent requests, a 12 MiB response bound, a 30-second deadline, and cancellation on close limit work. Reverification, cookie reset, transport failure, HTTP error or a non-JSON-shaped response clears the saved route. A changed cookie at the exact requested URL advances the in-memory image-cache session revision; cookies scoped exclusively to other paths cannot be detected by that comparison.

This is a limited fallback for these public text endpoints, not a general-purpose browser proxy. It does not prove a server will permit its API, work around a required VPN, or guarantee image CDN access. A browser challenge may still require user interaction and can reject an API fetch even when a normal page opens. The route needs live verification on the affected device and network before claiming the reported connection failure is resolved.

Android's native Activity privacy cover remains responsible for the resume transition and Recents protection. Flutter no longer draws a second branded cover underneath it on Android; the Flutter cover remains active for non-Android platforms.
