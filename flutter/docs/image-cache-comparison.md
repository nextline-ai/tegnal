# Image cache comparison

The native iOS manga reader's `PageImageStore` keeps decoded images in an `NSCache` (192 MiB cost limit and 128 entries) and uses a 512 MiB disk cache keyed by page hash and thumbnail/full-image variant. Its shared requests support cancellation when no consumers remain, and reader prefetch is constrained by power and thermal state. The native disk cache can be reused after a process restart.

Flutter shares decoded images through Flutter's `ImageCache`. Flutter's decoded limit is raised to the native 192 MiB because the default 100 MiB holds only about four full reader pages. Its session image loader also keeps up to 32 MiB of encoded bytes in memory and 512 MiB in the app's temporary cache directory. Requests with the same URL, headers, size limit, and session revision share a load. A disk hit lets an image decode again after the decoded image or memory bytes are evicted. Disk persistence runs after bytes are handed to the decoder, with at most sixteen queued writes and 32 MiB of queued image bytes. The disk index is built before the first write and updated incrementally, so a launch that only reads never scans the directory; writes are best effort and may be skipped under load. The network queue permits six active image jobs, matching the native content transport. Thumbnails stop at five, so a reader page always has a slot and runs ahead of waiting thumbnails.

Known disk misses now bypass cache-file indexing and unrelated queued writes, while a request for a key already being written still waits to reuse that data. Initial disk-index metadata requests run in batches of 32. Disk hits update the file's modified time, which carries recency across restarts. On an OS memory-pressure notification, the encoded memory cache is cleared along with Flutter’s independently managed decoded cache; disk entries and active requests remain. Concurrent WebView header lookups for the same exact URL and session revision share only their in-flight call; completed cookie values are not cached, and cookie-change comparisons bypass this sharing. These behaviors have focused deterministic tests; they have not been measured as device frame-time improvements.

Anonymous entries survive a restart: requests without `Cookie` or `Authorization` headers, made before browser authentication changed in this process, use a stable hashed filename. All other entries keep a random process-session component and cannot be reused by a later process. Android adds WebView cookies at the transport, below this key, so a stable entry may have been fetched with a site session; resetting a site's cookies therefore clears the whole cache. Old entries remain eligible for space-based eviction or explicit cache clearing. Authentication headers participate in the key, browser-session changes invalidate the affected session scope, and Android cross-origin redirects are not encoded-cached because their destination cookies can change independently. Responses marked `no-store`, `no-cache`, or `Vary: *` are not retained in the encoded tiers. Freshness uses `max-age`, `Age`, and `Expires` when supplied; otherwise it defaults to one hour, capped at seven days. This cache does not implement conditional revalidation. Flutter's decoded-image cache has its own lifecycle and is cleared together with these encoded tiers by the settings action.

These mechanisms reduce repeat transfers in covered cases; they do not guarantee a particular frame rate. Device measurements are in [ui-release-performance.md](ui-release-performance.md). Android requests a supported same-resolution mode using [`preferredDisplayModeId`](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#preferredDisplayModeId), a preference the system can decline or change according to device policy.
